# LEADUP CRM — база в Supabase

Схема целиком — `migrations/20260921000001_crm_schema.sql`: таблицы, права (RLS), защита полей, RPC, realtime.
Старые файлы Vexa лежат в `_vexa_archive/` — к CRM они не относятся, в новый проект их не запускать.

## Подключение (один раз)

Регистрации в CRM нет — только вход. Вход сотрудникам создаёт руководитель.

1. **SQL.** Supabase → SQL Editor → New query → вставить `migrations/20260921000001_crm_schema.sql` целиком → Run.
   Повторный запуск безопасен.
2. **Функция входа сотрудников.** Supabase → Edge Functions → Deploy a new function → Via Editor →
   имя `crm-users` → вставить `functions/crm-users/index.ts` → Deploy.
   (CLI: `supabase functions deploy crm-users`.) Секретные ключи функция берёт из окружения Supabase сама.
3. **Закрыть регистрацию.** Authentication → Sign In / Providers → выключить «Allow new users to sign up».
   Функция `crm-users` создаёт пользователей и при выключенной регистрации.
4. **Ключи** уже в `.env.local` (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`).
   Publishable-ключ публичный: данные защищает RLS, а не ключ. Secret-ключ в приложение не класть.
5. **Руководитель.** Authentication → Users → Add user → Create new user: своя почта, пароль,
   галочка «Auto Confirm User». Войти в CRM — первый вошедший в пустую базу становится РОПом.
6. **Сотрудники.** «Настройки → Аккаунты → Новый аккаунт»: имя, почта, роль, пароль (кнопка
   «Сгенерировать»). Почту и пароль передать человеку — он входит на `/login`. Сменить пароль —
   там же, поле «Новый пароль».
7. **Telegram (Vexi).** Там же в SQL Editor выполнить `migrations/20260923000001_telegram_link.sql`
   (после основной схемы; повторный запуск безопасен). Добавляет привязку Telegram оператора
   (`operator_telegram`), одноразовые коды (`telegram_link_codes`, только хэш), архив отвязок и RPC
   `crm_telegram_link_create / crm_telegram_status / crm_telegram_unlink` (CRM) и `telegram_link_consume`
   (только бот, service_role). Оператор видит лишь свою привязку; Telegram ID другим не отдаётся.
8. **Найм (кандидаты).** Если схема ставилась до появления раздела «Найм» — выполнить
   `migrations/20260924000001_candidates.sql` (повторный запуск безопасен, данные не трогаются). Добавится
   таблица `candidates` и её права: РОП — все, супервайзер с правом вести операторов — только кандидаты своих групп.
   Всю схему заново при открытой CRM не запускайте: она пересоздаёт политики на всех таблицах и ловит deadlock.
   Пока таблицы нет, CRM работает как раньше, а «Найм» показывает подсказку.
9. **Ссылка на лид и время по Москве.** Выполнить `migrations/20260925000001_lead_link_time.sql`
   (повторный запуск безопасен). Добавится колонка `leads.link`, а триггер лидов начнёт сам ставить время
   лида оператора — «сейчас» по Москве по часам сервера; при правке оператор время не меняет. Пока файл не
   выполнен, лиды сохраняются без ссылки (CRM не встаёт), время ставит сама CRM по серверу.
10. **Старые данные из браузера** (если работали без базы): «Настройки → Данные → Перенести в базу».
11. **Разговор в карточке лида (Скорозвон → Memo AI).** Оператор вставляет ссылку из звонка
    `…/#/leads/<лид>/answer/<звонок>/+7…`, а в карточке лида появляется запись и расшифровка по репликам.
    - SQL Editor: выполнить `migrations/20261005000001_lead_dialogs.sql` (таблица `lead_dialogs`; повторный запуск безопасен).
    - Edge Functions → Secrets: `SKOROZVON_USERNAME` (логин Скорозвона), `SKOROZVON_API_KEY`, `SKOROZVON_CLIENT_ID`
      (ID приложения), `SKOROZVON_CLIENT_SECRET` (ключ приложения) — всё из Скорозвона «Интеграции → API»;
      `MEMO_API_KEY` — Memo AI → API, ключ с правом «Загрузка».
    - Edge Functions → Deploy a new function → Via Editor → имя `lead-dialog` → вставить
      `functions/lead-dialog/index.ts` → Deploy.
    Минуты списываются с баланса Memo AI (≈ длительность разговора). Пока чего-то нет, CRM работает как раньше,
    а в карточке лида вместо разговора написано, чего не хватает.
12. **Разбор разговора: сводка и чек-лист (карточка лида «Проверка»). Пока выключен.**
    Включить: `SHOW_REPORT = true` в `components/app/LeadDialog.tsx` и шаги ниже.
    - SQL Editor: выполнить `migrations/20261006000001_lead_dialog_report.sql` (колонки `report_status`, `report`).
    - Edge Functions → `lead-dialog` → вставить свежий `functions/lead-dialog/index.ts` → Deploy.
    - Memo AI → Настройки → AI-отчёты → новый шаблон, название **«Проверка лида»**, опубликовать на весь workspace.
      Его идентификатор (обычно `proverka-lida`) положите в секрет `MEMO_REPORT` — без секрета разбор не заказывается.
      У ключа `MEMO_API_KEY` должно быть право «AI-отчёты». Текст шаблона:

      ```
      Ты проверяешь телефонный разговор оператора колл-центра с клиентом: оператор квалифицирует
      клиента на покупку автомобиля и передаёт его менеджеру. Ответь строго в формате ниже,
      по строке на пункт, без вступлений, пояснений и markdown, на русском.

      СВОДКА: 2–3 предложения — что хочет клиент, ключевые условия и о чём договорились.
      ИМЯ: да/нет | как зовут клиента | мм:сс
      ИНТЕРЕС: да/нет | интересует ли покупка: новый или с пробегом | мм:сс
      МОДЕЛЬ: да/нет | марка, модель или класс автомобиля | мм:сс
      БЮДЖЕТ: да/нет | сумма | мм:сс
      СРОК: да/нет | когда планирует покупку | мм:сс
      ОПЛАТА: да/нет | наличные, кредит или трейд-ин | мм:сс
      ЗВОНОК МЕНЕДЖЕРА: да/нет | согласен ли на звонок менеджера и когда удобно | мм:сс
      ИТОГ: доведён / не доведён / под вопросом — одна фраза, почему

      «да» — пункт выяснен в разговоре, «нет» — оператор не выяснил или клиент не ответил.
      мм:сс — время реплики, где это прозвучало. Если пункт не выяснен, во втором поле напиши
      «не выяснили», а время оставь пустым.
      ```

      Пункты можно менять: карточка показывает те строки «ПУНКТ: да | значение | мм:сс», что пришлют.
    Разбор приходит через 30–60 секунд после расшифровки. Для старых лидов карточка закажет его сама при открытии.
    Нет шаблона — карточка пишет «Разбора нет» и даёт кнопку «Запросить разбор»: создали шаблон — нажали.

## Кто что видит

| | РОП | Супервайзер | Оператор |
|---|---|---|---|
| Лиды | все | своих групп | свои |
| Статус лида (доведён / не доведён) | любой | своих групп, кроме своих лидов | нет |
| Операторы, график, планы | все | своих групп | свои |
| Начисления, зарплата | все | своих групп, если разрешено | свои, если разрешено |
| Кандидаты (найм) | все | своих групп, если может вести операторов | нет |
| Аккаунты, настройки, журнал | да | журнал — если может править зарплату | нет |

Флаги «что можно супервайзеру / оператору» — в CRM, «Настройки → Роли и доступ»; база читает их же.

## Таблицы

`operators`, `groups`, `projects`, `leads`, `shifts`, `plans`, `adjustments`, `accounts`, `learn`,
`approves`, `audit`, `kv` (настройки: `settings`, `sheets` — секреты выгрузки, видит только РОП; `frozenMonths`).
Колонки — те же поля, что в `lib/crm/types.ts`, в snake_case. Время передачи лида `leads.at` — текст
`YYYY-MM-DDTHH:mm` (локальное, как в приложении).
